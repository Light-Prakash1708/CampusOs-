# Deploying CampusOS on Render

CampusOS is one Next.js service plus PostgreSQL, managed with Drizzle
migrations. `render.yaml` in the repository root is a Render Blueprint that
creates everything in one step. Operations, backups and rollback are covered
in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## What the Blueprint creates

| Resource | Type | Settings |
|---|---|---|
| `campusos` | Web service, Node | Build `npm ci --include=dev && npm run build` · Pre-deploy `npm run db:migrate` · Start `npm start` · Health check `/api/health` · Node 22 (`NODE_VERSION` and `.node-version`) |
| `campusos-jobs` | Cron job, every 10 min | `curl -X POST …/api/jobs/run` with the `x-cron-secret` header, over Render's private network |
| `campusos-db` | Render Postgres 16 | Database `campusos`, user `campusos`, internal connections only |

All three are in the `singapore` region, which is closest to India. To change
the region, edit it in all three places before the first deploy; a
database's region can't be changed later.

`npm start` runs `next start -p ${PORT:-3000}`. Render sets `PORT`, so no
port needs configuring.

## Step by step

1. **Push the repository to GitHub** (or GitLab) with `render.yaml` at the root.
2. In Render, choose **New → Blueprint** and select the repository and branch.
3. Render lists the resources above and asks for every `sync: false`
   variable. **Leave all of them blank for a first deploy.** The app runs
   without any of them (see "Secrets you enter manually" below).
4. Click **Apply**. Render then:
   1. creates the database;
   2. builds the app;
   3. runs `npm run db:migrate` (the pre-deploy step);
   4. starts the server;
   5. waits for `/api/health` to return 200 before sending traffic.
5. Open `https://<service>.onrender.com/api/health`. You should see
   `"status":"healthy"` with `pending: 0` migrations.
6. **Create the first college and its administrator.** Open the web service →
   **Shell**, then run:

   ```bash
   npm run provision -- --slug kbi --name "Kolkata Business Institute" --short KBI \
     --city Kolkata --admin-email registrar@kbi.edu.in --admin-first Anita --admin-last Roy
   ```

   It prints a one-time invitation link, valid for 7 days. Open it and set the
   password. **Never run `db:seed` in production**: it loads demo data.
7. Optional: attach a custom domain (Settings → Custom Domains), then set
   `APP_URL=https://campus.example.edu` on **both** the web service and the
   cron job and redeploy.

## Environment variables

`src/lib/env.ts` validates configuration when the server starts. In
production, an invalid configuration stops the process with a list of what to
fix. That list appears in the deploy log, and the release never takes traffic.

### Required (all provided by the Blueprint)

| Variable | Where it comes from |
|---|---|
| `DATABASE_URL` | **The production database variable.** Wired automatically from `campusos-db` (internal connection string). For Supabase, paste the **session pooler** URL, port 5432. |
| `AUTH_SECRET` | Generated by Render (at least 32 characters). Signs sessions; changing it signs everyone out. |
| `CRON_SECRET` | Generated by Render and shared with the cron job. |
| `APP_URL` | Optional on Render. When blank, Render's `RENDER_EXTERNAL_URL` (`https://<service>.onrender.com`) is used. Set it for a custom domain. |
| `NODE_ENV` | `production` |

### Fixed values in the Blueprint

| Variable | Value | Why |
|---|---|---|
| `NODE_VERSION` | `22` | Node runtime |
| `DATABASE_SSL` | `require` | TLS to Postgres (use `verify` plus `DATABASE_CA_CERT` for full verification) |
| `DB_POOL_MAX` | `10` | Connections per instance; keep below the database's limit |
| `DEMO_MODE` | `false` | Refused in production |
| `TRUST_PROXY` / `TRUSTED_PROXY_HOPS` | `true` / `1` | Real client IP behind Render's proxy; `2` if Cloudflare is in front |
| `SESSION_MAX_AGE` | `28800` | 8-hour sessions |
| `NEXT_PUBLIC_DEFAULT_TIMEZONE` | `Asia/Kolkata` | Display timezone; **read at build time**, so change it and redeploy |
| `MALWARE_SCANNER` | `signature` | Built-in checks on uploads |
| `AI_PROVIDER` | `local` | Offline assistant; no key needed |
| `STORAGE_PROVIDER` | `none` | Uploads off until storage is configured |
| `EMAIL_PROVIDER`, `PUSH_PROVIDER`, `SMS_PROVIDER`, `WHATSAPP_PROVIDER`, `ERROR_REPORTER`, `OPPORTUNITY_FEED_PROVIDER` | `none` | Integrations off; the product says the feature isn't available rather than failing |
| `LOG_LEVEL`, `NEXT_TELEMETRY_DISABLED` | `info`, `1` | |
| `SELF_REGISTRATION_ENABLED` | `true` | Students can create their own account without a college (a private workspace); `false` keeps sign-up to college invitations and registration policies |

### Secrets you enter manually (all optional)

Each is declared `sync: false`, so it never lives in the repository. Enter it
in Render → service → **Environment** only when you switch that integration
on, and change the matching provider variable at the same time. If a provider
is selected without its credentials, the server refuses to start and names
the missing variable.

| To enable | Set the provider to | Then enter |
|---|---|---|
| AI assistant (Claude) | `AI_PROVIDER=anthropic` | `ANTHROPIC_API_KEY` |
| File uploads (Supabase Storage) | `STORAGE_PROVIDER=supabase` | `STORAGE_ENDPOINT` (`https://<ref>.supabase.co/storage/v1/s3`), `STORAGE_REGION`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY` |
| File uploads (S3 or R2) | `STORAGE_PROVIDER=s3` | the same five `STORAGE_*` variables |
| Email | `EMAIL_PROVIDER=resend` | `RESEND_API_KEY`, `EMAIL_FROM` (e.g. `CampusOS <no-reply@campus.example.edu>`) |
| Push | `PUSH_PROVIDER=fcm` | `FCM_PROJECT_ID`, `FCM_CLIENT_EMAIL`, `FCM_PRIVATE_KEY` |
| SMS | `SMS_PROVIDER=msg91` | `MSG91_AUTH_KEY`, `MSG91_TEMPLATE_ID` |
| Error forwarding | `ERROR_REPORTER=webhook` | `ERROR_WEBHOOK_URL` |
| Opportunities feed | `OPPORTUNITY_FEED_PROVIDER=json-feed` | `OPPORTUNITY_FEED_URL` (https), `OPPORTUNITY_FEED_TOKEN` |
| Custom domain | — | `APP_URL`, on the web service **and** the cron job |

Never put a secret in a `NEXT_PUBLIC_*` variable: those are compiled into the
browser bundle.

## First accounts

A fresh database has **no accounts**, so every sign-in fails with "That email
and password combination is not correct" until someone exists:

- **Students** can create their own account at `/register` when
  `SELF_REGISTRATION_ENABLED=true`.
- **A college** is created with `npm run provision` (see step 6 above). Its
  administrator then invites staff and students, or opens registration.

## Database and migrations

- **Migration command:** `npm run db:migrate`. The Blueprint runs it as the
  **pre-deploy command** on every deploy, before the new release takes
  traffic.
  - The migrations in `drizzle/migrations` are forward-only and additive, and each one runs in a transaction.
  - They are recorded in `drizzle.__drizzle_migrations`, so a re-run applies nothing.
  - If a migration fails, the deploy stops and the previous release keeps serving.
- **Safety net:** `/api/health` compares applied migrations with the ones the
  build expects, and returns 503 `migrations_pending` until they match.
- **No pre-deploy step?** Pre-deploy commands need a paid instance type. On a
  free instance, set the start command to `npm run db:migrate && npm start`.
  That is safe because the runner is idempotent.
- **Access:** the database accepts internal connections only
  (`ipAllowList: []`). To reach it from your own machine, for example for
  `pg_dump`, add your IP under the database's **Networking** settings, then
  use the external URL with `DATABASE_SSL=require`.
- **Supabase instead of Render Postgres:**
  1. Delete the `databases:` block in `render.yaml`.
  2. Replace the `DATABASE_URL` entry with `- key: DATABASE_URL` / `sync: false`.
  3. Paste the Supabase **session pooler** URL (port 5432) when prompted. The transaction pooler (6543) does not support the migration runner.
  4. `db:migrate` also revokes Supabase's `anon`/`authenticated` roles and enables RLS, so the public Data API can't read CampusOS tables.

## Health check

- **URL:** `https://<service>.onrender.com/api/health` (Render's health check path is `/api/health`).
- **200** `healthy`: the database is reachable and fully migrated.
- **503** `migrations_pending`: the schema is behind this build.
- **503** `unhealthy`: the database is unreachable.
- The response includes the release (`RENDER_GIT_COMMIT`), database latency and migration counts. It never includes secrets or connection strings.

## Production error handling

- **Invalid configuration:** the server exits at boot with the list of problems, so the deploy fails visibly.
- **API errors:** a consistent JSON shape (`{ ok:false, error:{ code, message } }`) with a request id. Stack traces are never sent to clients.
- **Page errors:** `error.tsx`, `global-error.tsx` and `not-found.tsx` render friendly pages.
- **Reporting:** server render errors (`onRequestError`), unhandled promise rejections and uncaught exceptions go to `reportError`. They are logged as JSON, and forwarded to `ERROR_WEBHOOK_URL` if it is set. After an uncaught exception, the process exits and Render restarts it.
- **Logs:** Render → service → Logs. Passwords, tokens, cookies and keys are redacted by key name.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Deploy log shows `Invalid CampusOS configuration` | Set the named variable. The message says why it is needed. |
| `DATABASE_URL is not set.` during pre-deploy | The database link is missing. Re-apply the Blueprint, or set `DATABASE_URL` by hand. |
| Health check returns `migrations_pending` | Run `npm run db:migrate` from the Shell, or redeploy. |
| `self-signed certificate` errors | Keep `DATABASE_SSL=require`. Use `verify` only together with `DATABASE_CA_CERT`. |
| Cron job fails with 401 | `CRON_SECRET` differs between the services. Re-sync it from the web service. |
| Cron job can't connect | Set `APP_URL` on the cron job to the public URL. |
